# Zebra Launcher: plan to make it a stable, maintained product

## Context

Zebra Launcher (this repo) is a Tauri desktop app that installs and runs `zebrad`, shows its logs, and lets the user edit `zebrad.toml` and restart the node. It stalled at v0.0.0-alpha.4 (2024-12-09): it pins Tauri 2.0.0-beta.6/beta.7 and `@tauri-apps` beta npm packages with open-ended `>=2.0.0-beta.0` ranges, dependabot churn was never merged, macOS builds were unsigned and would not open (issue #27), and the backend has debts: `std::sync::Mutex<Option<Child>>` state (`src-tauri/src/state.rs`), config and binary resolved next to the executable (`src-tauri/src/child_process.rs:34-54`, read-only on installed macOS/Windows/deb apps), `SIGKILL` with no `wait()` and hardcoded 3 s/5 s sleeps, stderr piped but never drained (can block zebrad), every failure an `expect()` before any window opens, no tracing subscriber, CSP `null`, `tauri-plugin-shell` depended on but never registered, and ~157 MB of zebrad binaries committed (`src-tauri/binaries`, .git is 179 MB, no macOS binary at all). CI only builds and deploys a browser demo to Cloud Run (always-on prod instance, GCP secrets); nothing checks the Rust code or builds a bundle.

Decisions locked by the maintainer:

- **Tauri 2 stable**, own window with a web rendering engine, native installers that need neither Rust nor Node on the user's machine.
- **Lives in this repo** with its own CI (keeps webkit2gtk/GTK out of the Zebra workspace).
- **Features:** supervise a bundled `zebrad`; stream logs; view/edit config and restart; metrics in the GUI with a **Grafana iframe** as the easy path (user-run Grafana, no bundling); **optional auto-updates** (opt-in).
- **Stable and easy to maintain** by a small Rust team for years. **No mutexes** in Rust code.
- **Signing available:** Apple Developer ID + notarization; Windows via Azure Artifact Signing (SignPath only as fallback: it needs one manual approval per signing request, which conflicts with Tauri's per-file `signCommand`).
- **Platforms:** macOS Apple Silicon, macOS Intel, Windows x64, Linux x64 and arm64.
- **Frontend: Leptos CSR.** **Graceful stop: upstream opt-in "shut down when stdin closes" in zebrad.** **Linux packaging: AppImage + deb** (AppImage auto-updates, deb is Notify-only).

Zebra-side facts (verified against the zebra checkout and release workflows): release binaries exist only for Linux x86_64/aarch64 (tarball + `SHA256SUMS` + Sigstore keyless bundle + SLSA attestation, built on ubuntu-22.04, glibc floor 2.34); macOS and Windows are Tier 3 with no CI builds; ADR 0008 prefers keyless signing; on **Mainnet only**, `zebrad` warns 42 days and **halts 56 days** after its estimated release height (`end_of_support.rs`), so a desktop install that does not update stops working; every zebrad config section is `deny_unknown_fields` and a bad config exits 1; RPC is off by default and cookie-authenticated; on Windows zebrad only handles Ctrl-C, which a console-less GUI parent cannot deliver reliably; nothing in `zebrad/src` reads stdin today.

## Frontend: Leptos CSR with guardrails

Facts from a dedicated research pass (sources: crates.io, leptos release notes, `create-tauri-app` templates, trunk releases): Leptos 0.8.22 stable, 0.9.0-rc0 out, MSRV 1.88, one breaking minor every 6–12 months (0.7 was a near-rewrite, 0.8 and 0.9 mild). `create-tauri-app` ships an official Leptos template (`trunk serve`/`trunk build`, `frontendDist ../dist`, `withGlobalTauri true`, hand-written `#[wasm_bindgen]` externs to `window.__TAURI__`). `tauri-sys` is git-only and partial. Trunk 0.22.0 (2026-10-20) ended a 17-month release gap; wasm-bindgen crate and CLI must match exactly, which Trunk handles if `[tools].wasm_bindgen` stays unpinned. A CSP must include `'wasm-unsafe-eval'`.

Guardrails: CSR-only (`leptos` with `csr`, no SSR/server functions); hand-written externs to `window.__TAURI__.core.invoke` and `window.__TAURI__.event.listen` (~100 lines, no `tauri-sys`); a shared `launcher-types` crate so IPC payloads are compile-checked on both sides (JSON-compatible `serde-wasm-bindgen` serializer; no `tokio`/`tauri` in that crate); trunk auto-detects `wasm-bindgen-cli` from `Cargo.lock`; `trunk` and `tauri-cli` installed with `cargo binstall` at pinned versions in CI; all parsing/validation logic in native-testable crates; keyed `<For>` over a 1 000-line capped log list; dependabot groups `leptos*` with the `wasm-bindgen` family. Budget one Leptos breaking-minor migration a year.

## Recommended approach

### Shape

A Cargo workspace with four crates and no Node toolchain:

```
Cargo.toml                 workspace: crates/*, src-tauri, ui (resolver 3, [workspace.package] version = single version source)
rust-toolchain.toml        pinned stable (>= 1.90 for tauri 2.12; >= 1.91 so the same toolchain can build zebrad 7.x)
ZEBRAD_VERSION             e.g. 7.0.0 — the only place the bundled zebrad version lives
deny.toml                  cargo-deny: advisories, licenses, duplicate tauri/wry/tao majors
crates/launcher-types/     serde structs shared by backend and UI (Status, LogLine, Settings, NodeStats, errors); no tokio/tauri
crates/launcher-core/      Tauri-free logic: supervisor actor, process (unix/windows), logs, config, rpc, settings, paths, eos, install-kind
  src/bin/fake-zebrad.rs   scripted stand-in for zebrad used by tests and PR bundle builds
  tests/                   integration tests with timeouts on every await; fixtures captured from real zebrad 7.0.0
src-tauri/                 thin Tauri 2.12 app: commands, Channel bridge, tray, updater, exit flow, capabilities, icons (kept)
  binaries/.gitignore      zebra-launcher-zebrad-<triple> populated by scripts, never committed
ui/                        Leptos CSR crate built by trunk into ui/dist
scripts/                   fetch-zebrad-linux.sh (cosign verify), build-zebrad.sh/.ps1, dev-sidecar.sh (fake), check-versions.sh
docs/                      ARCHITECTURE.md, DEVELOPMENT.md, RELEASING.md, SECURITY.md, GRAFANA.md, TROUBLESHOOTING.md, UNINSTALL.md
```

Deleted: all Cloud Run/Docker/super-linter workflows, `docker/`, `package.json`, `pnpm-lock.yaml`, `vite.config.ts`, `tsconfig*`, `src/`, root `index.html`, committed zebrad binaries (history is not rewritten).

### Supervisor (launcher-core, no mutexes)

- One actor task owns the child. Commands arrive on an `mpsc` (`Start`, `Stop`, `Restart`, `ApplyConfig`, `Shutdown`); state is published on `watch<Status>` (`Stopped`, `Starting`, `Running{pid, since, rpc_ready}`, `Stopping`, `Exited{code, class}`, `Failed{class}`); log lines go into a `VecDeque` ring (10 000 lines, monotonic `seq`) plus a `broadcast` for live subscribers; late subscribers get `History{since}` through a `oneshot`. A rotating `zebrad.log` file is written for post-crash support.
- Spawning happens on one dedicated long-lived OS thread (the "spawner") using `std::process::Command`, then `tokio::process::Child::from_std`. This thread is where Linux `PR_SET_PDEATHSIG(SIGTERM)` is set in `pre_exec` (PDEATHSIG fires when the spawning *thread* exits, so it must never be a tokio blocking-pool thread) and where Windows creates a **per-zebrad** Job Object with `CREATE_SUSPENDED` → assign → resume, the way `zebra-test/src/command/process_group/windows.rs` does it. The launcher itself is never placed in a job (that would kill the NSIS updater and opened browsers when the app exits). `KILL_ON_JOB_CLOSE` is set only while the pinned zebrad lacks the stdin-close mode; once it has it, the job is kept for escalation only so a launcher crash lets zebrad shut down gracefully via stdin EOF. Windows keeps `CREATE_NO_WINDOW` from the current `child_process.rs`.
- Both stdout and stderr are drained by reader tasks and joined to EOF before an exit is classified. Classifiers are anchored on level and target, not bare substrings: `ConfigError` (`Zebra could not load the provided configuration`), `EosHalt` (`Zebra refuses to run`), `EosWarn` (`Your Zebra release is too old`), `PortInUse`, `DbLocked` (`Database likely already open`), `BinaryMissing`. Deterministic failures (`ConfigError`, `EosHalt`, `PortInUse`, `DbLocked`, `BinaryMissing`, disk full) set `Failed` and are never retried; crashes use 1→60 s backoff and give up after 5 in 10 minutes.
- Graceful stop, primary mechanism: zebrad is spawned with the upstream opt-in stdin-close flag and a piped stdin; `Stop` drops the write end, waits up to the grace period (default 60 s; zebrad's own tokio shutdown timeout is 20 s; measured on a real node in M3), then kills (`SIGKILL` / `TerminateJobObject`) and `wait()`s. One mechanism on all three OSes; a launcher crash closes the pipe too. Until the pinned zebrad includes the change: Unix sends `SIGTERM`; Windows terminates the job and the UI labels it a hard stop.
- Orphan protection, defence in depth: PDEATHSIG (Linux), the per-zebrad job (Windows), and a pidfile on all OSes; on startup a stale zebrad is detected and the user is offered "wait for it to exit" or "kill" (an orphan cannot be adopted: its pipes are gone).
- zebrad is spawned with `-c <app_config_dir>/zebrad.toml start`, `env_remove` for every inherited `ZEBRA_*` variable (never `env_clear`, which would drop `PATH`, `HOME`, `SystemRoot`, `LOCALAPPDATA` that zebrad's `dirs::` defaults need), and launcher invariants forced through env vars that beat the file: `ZEBRA_TRACING__USE_COLOR=false`, `ZEBRA_TRACING__PROGRESS_BAR` and `ZEBRA_TRACING__LOG_FILE` unset.
- AppImage: the sidecar is copied out of the FUSE mount into the app data dir (hash-checked, per launcher version) and spawned from there, so zebrad survives the mount disappearing when the launcher exits or is replaced by an update; exit still waits for zebrad (escalating to kill).
- Patterns copied (not depended on) from `zebra-test/src/command.rs` `TestChild`: deadline on every read, kill-on-drop safety net, process group / job object, `watch` for cancellation.

### Upstream zebrad change (M6, this maintainer owns it)

Opt-in flag on `StartCmd` (`zebrad/src/commands/start.rs:119-131`, beside `--zcashd-compat`) or config key: when set, a detached `std::thread` reads stdin to EOF (read errors count as EOF) and signals a `oneshot`/`watch` that is selected alongside the signal handlers' result in `RuntimeRun::run` (`zebrad/src/components/tokio.rs:62-73`); it must not go unconditionally into `imp::shutdown` because `copy-state` uses `RuntimeRun` too. The path does what the signal handlers do: `zebra_chain::shutdown::set_shutting_down()`, disable howudoin, log `target: "zebrad::signal"` "stdin closed, starting shutdown" so the launcher classifier can match it. Do not use `tokio::io::stdin()` or `spawn_blocking` (a never-finishing blocking read makes `rt.shutdown_timeout(20s)` wait the full 20 s on every signal shutdown). Log loudly if EOF arrives within the first second (started without a real stdin). Windows: `ERROR_BROKEN_PIPE` maps to `Ok(0)`, so dropping the write end is EOF; std makes only the child's pipe end inheritable, so concurrent spawns cannot keep it open. Add a zebrad acceptance test with `TestChild` (piped stdin, drop, expect the log line and exit 0); it runs only on Linux in Zebra CI, so the launcher's `bundle.yml` runs the real-zebrad stdin-close check on Windows and macOS.

### Config (launcher-core/config.rs)

- The launcher writes a **minimal** `zebrad.toml` containing only the keys it manages plus the user's edits, never the full `zebrad generate` output (avoids the `deny_unknown_fields` trap when a zebrad bump drops a defaulted key). Managed keys: `network.network`, `rpc.listen_addr = 127.0.0.1:8232` (18232 testnet), `rpc.enable_cookie_auth = true`, `rpc.cookie_dir = <app_local_data_dir>/rpc`, `metrics.endpoint_addr = 127.0.0.1:9999`, `state.cache_dir = <chosen data dir>/state`; `zcashd_compat` is unsupported and forced off (its 300 s shutdown grace would exceed the launcher's). `zebrad generate` output is shown read-only as reference in the editor.
- `PortInUse` remediation: the launcher offers alternative RPC/metrics ports, writes them into the managed keys, and the Grafana compose file is parameterised to match. The RPC address always comes from the config the launcher wrote, never from log lines.
- Edits: TOML syntax check, atomic write (temp + rename, `.bak` kept), compare-and-swap token from `read_config` so an external edit is not silently overwritten, graceful restart, 20 s watch; on `ConfigError` the `.bak` is restored and zebrad restarted, and the UI shows zebrad's stderr text plus "rolled back". A pending-apply marker makes a crash mid-apply roll back on next launch.
- Security-relevant managed keys are enforced, not warned: RPC/metrics/health must be loopback and cookie auth on, or the save is refused with an explanation.
- On a bundled zebrad version change, the config is validated against the new zebrad (10 s probe run) before the normal start; if it fails, the launcher regenerates the managed keys, keeps the user's other keys, and shows what changed.
- First run: data-dir chooser with free-space check (Mainnet state is hundreds of GB; default `app_local_data_dir`, never the purgeable macOS `~/Library/Caches`, never a CLI zebrad's existing state, which would share the RocksDB lock), network choice, a note about the OS firewall prompt for the P2P listener on `[::]:8233`, and alpha.4 detection: if `zebrad.toml` sits next to an old `zebra.app` install or a launcher-created state exists at the default `dirs::cache_dir()/zebra`, offer to move it into the new data dir (a same-volume rename, after checking no zebrad is running), delete it, or ignore it, showing its size. The update-mode choice is added to first run in M11.

### Status, metrics, Grafana

- `rpc.rs` + `monitor.rs`: cookie-auth JSON-RPC poller (reqwest/rustls) every 5 s for `getblockchaininfo`, `getinfo`, `getmempoolinfo`, `getpeerinfo` count, hourly `getdeprecationinfo` (Mainnet only; Testnet shows no EOS countdown); publishes `watch<NodeStats>`. `getinfo.errors` gives the last warn/error for free.
- Dashboard page: status strip (phase, height / estimated height, sync %, peers, mempool, versions, EOS countdown), Start/Stop/Restart, last error, and a Grafana `<iframe>` (kiosk URL of the `zebra-overview` dashboard, `sandbox="allow-scripts allow-same-origin"` so Grafana keeps its own origin, cookies and API calls; no top-navigation or popups; no referrer) shown only when `settings.grafana_url` is set. The CSP is build-time, so `frame-src` is a static loopback allow-list (`http://127.0.0.1:* http://localhost:*`) and the settings validator refuses non-loopback Grafana URLs. The iframe gets no IPC (no remote capability).
- `docs/observability/docker-compose.yml`: Prometheus + Grafana reusing Zebra's `docker/observability/grafana` dashboards and provisioning (datasource uid `zebra-prometheus`), `GF_SECURITY_ALLOW_EMBEDDING=true`, anonymous Viewer, loopback-only ports, and a scrape target that reaches the host: `network_mode: host` on Linux; `host.docker.internal:9999` on Docker Desktop (whether Docker Desktop reaches a host service bound to 127.0.0.1 this way is **verified in M7**; the fallback is a documented metrics bind on the Docker bridge address). Verified early on all three OSes, including macOS mixed content (`http://127.0.0.1:3000` inside `tauri://localhost`); fallback is an "Open in browser" button via `tauri-plugin-opener` from Rust.

### Tauri app (src-tauri)

- Dependencies: `tauri = "2.12"` (>= 2.11.1 for CVE-2026-42184; feature `tray-icon`; no `devtools`), `tauri-build = "2.7"`, `tauri-plugin-updater = "2.14"` (>= 2.12 for CVE-2026-95625), `tauri-plugin-process`, `tauri-plugin-single-instance`, `tauri-plugin-opener` (Rust-side only). Remove `tauri-plugin-shell` (its kill is SIGKILL-only and it was never registered).
- Commands: `get_status`, `start/stop/restart_zebrad`, `subscribe_logs` (`tauri::ipc::Channel<LogBatch>`, 100 ms batching, gap markers; events are not for high-throughput streams), `log_history`, `read_config`/`apply_config`/`reset_config`, `get_settings`/`set_settings`, `get_node_stats`, `check_update`/`install_update`, `open_path` (fixed set), `delete_node_data`. Capabilities list only these; `core:` prefixes; strict CSP with `'wasm-unsafe-eval'`.
- `identifier = "org.zfnd.zebra-launcher"`, `productName = "Zebra Launcher"`, `version` from Cargo (single source), `mainBinaryName` set, sidecar named `zebra-launcher-zebrad` so the `.deb` does not shadow `/usr/bin/zebrad`.
- Tray: menu Show / Start / Stop / Quit (Linux is menu-only), tooltip shows phase; `CloseRequested` → `prevent_close` + hide when close-to-tray is on and a tray exists (GNOME without appindicator falls back to quit). Quit and OS session end run the graceful stop with a short cap. `ExitRequested` guarded by an `AtomicBool`.
- Launcher's own tracing to `launcher.log` (tracing-subscriber + tracing-appender); a "copy diagnostics" action bundles launcher log, zebrad log tail, versions, config.
- Install kind detection uses Tauri's bundle type / the `APPIMAGE` env var, not the binary path, and drives Notify-only behaviour for deb.
- Uninstall: default data under `app_local_data_dir` so the NSIS uninstaller's "delete app data" option covers it; a user-chosen data dir is never removed automatically; Settings has "Delete node data"; `UNINSTALL.md` documents each OS, including alpha.4 leftovers.

### Updater (opt-in)

- Modes `Off` / `Notify` / `Auto`, default Off until the first-run prompt (Notify preselected). Off makes zero network requests (unit-tested with a mock endpoint). Notify checks at launch+30 s and every 6 h with jitter. Auto downloads in the background and installs at the EOS warning or on user click, with a cancellable countdown; never silently mid-session.
- Install sequence: `Update::verify` **before** stopping zebrad → graceful stop → install → `app.restart()`; if install fails, zebrad is restarted and the error shown. After restart, a health gate confirms zebrad reaches `Running` with RPC within 5 minutes or shows recovery UI (open logs, reset config, previous-installer link). `allowDowngrades = false`; roll-forward-only policy documented. The anti-rollback (signed-version) option's config key and what it requires to be signed are **verified in the plugin 2.14 source before M10**, because they may change how `latest.json` is assembled.
- Endpoint: `https://github.com/ZcashFoundation/zebra-launcher/releases/latest/download/latest.json` (this repo's latest non-prerelease release; release candidates are marked prerelease and rehearsed with a build-time endpoint override via `TAURI_CONFIG`, never a runtime env var honoured by release builds). UI warns when the last successful check is older than 14 days while EOS approaches.
- Updatable formats: AppImage (`linux-x86_64`/`linux-aarch64` keys point at the AppImage), NSIS per-user (Windows, no MSI, which also removes the NSIS-vs-MSI `latest.json` ambiguity), `.app.tar.gz` per arch (macOS). The `.deb` is Notify-only (shows the release link; deb updates need root) and declares `libwebkit2gtk-4.1-0`, `libgtk-3-0`, `libayatana-appindicator3-1`.

### Sidecar sourcing and release pipeline

- `ZEBRAD_VERSION` pins zebrad. Linux x86_64/aarch64 tarballs are downloaded from Zebra releases and verified with `cosign verify-blob SHA256SUMS --bundle SHA256SUMS.sigstore.json --certificate-identity https://github.com/ZcashFoundation/zebra/.github/workflows/zfnd-release-binaries.yml@refs/tags/v<ver> --certificate-oidc-issuer https://token.actions.githubusercontent.com` plus `gh attestation verify --repo ZcashFoundation/zebra --signer-workflow ZcashFoundation/zebra/.github/workflows/zfnd-release-binaries.yml`. macOS (aarch64, x86_64) and Windows x86_64 zebrad are built from the Zebra tag in `zebrad-sidecars.yml` (Zebra's pinned toolchain via `RUSTUP_TOOLCHAIN`, `--locked --features default-release-binaries`, `SOURCE_DATE_EPOCH`, protoc + LLVM on the runners), smoke-run (`--version`, `generate`, and once M6 ships, a stdin-close shutdown check), attested with `actions/attest-build-provenance`, and cached **unsigned** per zebrad tag. Signing of sidecars happens only inside the release environment, through the Tauri bundler (macOS codesign list includes sidecars; Windows `signCommand` is invoked for sidecars too).
- `release.yml` on `v*` tags: a first job creates the **draft** release once and passes `releaseId` to the matrix (parallel `tauri-action` jobs otherwise race and create duplicate releases). Compilation of untrusted dependency code (`cargo tauri build --no-bundle`) runs in unprivileged jobs with no secrets. Bundling and signing run in GitHub environment `release` (tag rule `v*`, required reviewer, self-review blocked) with **no caches restored**: `cargo tauri bundle` on the compiled artifacts does NSIS/dmg/AppImage/deb packaging, Windows `signCommand` (`azure/login@v3` OIDC + `artifact-signing-cli`), macOS codesign + notarization (App Store Connect API key) and updater `.sig` generation. Whether `tauri bundle` can consume the prebuilt binaries for every target is **verified in M9**; the fallback for a target is a full `tauri build` in the privileged job, still with no caches. `uploadUpdaterJson: false` on the matrix; a final job assembles `latest.json` from the `.sig` assets (tauri-action's per-job merge has no locking: issues #914, #1270), asserts all five platform keys are present, and adds `SHA256SUMS`, a keyless cosign bundle and attestations. A human smoke-tests and publishes; publishing is what makes `latest.json` live. tauri-action v1.0.0 renamed `includeUpdaterJson` to `uploadUpdaterJson` and `assetNamePattern` to `releaseAssetNamePattern`. Estimated cost per release with warm sidecar caches: 120–180 runner minutes, 40–60 min wall clock, free on a public repo.
- `RELEASING.md` includes the release-day runbook, the bad-release runbook (mark the release prerelease or re-point `make_latest` so `latest.json` moves, hotfix path with explicit sign-off that may skip the rc rehearsal, on-call owner), and the 14-day SLA after each zebrad release. The zebra repo's release checklist is the primary trigger; `zebrad-watch.yml` (daily schedule + dispatch) is the backstop: it compares Zebra's latest `v*` release with `ZEBRAD_VERSION` (filter on the tag pattern `^v\d+\.\d+\.\d+$`; zebra published `v7.0.0-rc.0` with `prerelease: false` per the releases API; the oldest release with assets is v6.4.2) and opens a bump PR using a GitHub App token (ZF already uses one in the zebra repo; `GITHUB_TOKEN`-created PRs do not trigger CI). Schedules pause after 60 idle days.
- Dependabot: cargo monthly with groups `tauri` (`tauri`, `tauri-*`, `wry`, `tao`), `wasm` (`wasm-bindgen*`, `js-sys`, `web-sys`, `leptos*`), `rust-other`; github-actions monthly, one group; cooldown 7 days; actions pinned by SHA. `scripts/check-versions.sh` asserts the `tauri-cli` version used in CI matches the `tauri` crate minor.

### CI

- `ci.yml` on PRs and `main`: Linux job in `container: ubuntu:22.04` on `ubuntu-24.04` (the `ubuntu-22.04` runner labels retire on 2027-04-17 per actions/runner-images issue #14254; the container keeps the glibc floor at 2.35, above zebrad's 2.34, so Ubuntu 22.04 and Debian 12 users stay supported) installs `libwebkit2gtk-4.1-dev libayatana-appindicator3-dev librsvg2-dev libxdo-dev libssl-dev`, builds `fake-zebrad` and copies it to `src-tauri/binaries/zebra-launcher-zebrad-<host triple>` first (tauri-build requires the sidecar file), then `cargo fmt --check`, `cargo clippy --workspace --all-targets -D warnings`, `cargo test --workspace`, `cargo deny check`, `trunk build` of `ui`; clippy `disallowed_types` bans `std::sync::Mutex`, `tokio::sync::Mutex`, `futures::lock::Mutex`, `RwLock`. `windows-2025` and `macos-15` jobs run `cargo clippy` + `cargo test -p launcher-core` so `cfg(windows)`/`cfg(target_os = "macos")` code is checked. PR CI takes 6–12 min with cache.
- `bundle.yml` (weekly + dispatch + on `ZEBRAD_VERSION` change + merges to `main`): unsigned bundles with the real zebrad on all five targets (Linux in `ubuntu:22.04` containers on `ubuntu-24.04` and `ubuntu-24.04-arm`, with `APPIMAGE_EXTRACT_AND_RUN=1`; `macos-15`; `macos-15-intel`; `windows-2025`), glibc floor check on Linux output, Linux install smoke under xvfb for both AppImage and deb (app starts, first log line appears, deb reports Notify-only), real-zebrad stdin-close shutdown check on Windows and macOS. No WebDriver E2E for now (macOS unsupported by tauri-driver, needs Node; revisit after 1.0).

## Risks

- **Tier-3 zebrad on macOS/Windows** may not build at a new tag while the 56-day clock runs. Mitigation: `bundle.yml` builds those targets weekly and on every `ZEBRAD_VERSION` bump; upstream issues filed early; ask Zebra to consider Tier 2 for these targets later.
- **Upstream stdin-close PR delayed.** Mitigation: the 1.0 gate above; SIGTERM on Unix and a labelled hard stop on Windows remain correct fallbacks (atomic WriteBatches make SIGKILL crash-safe, at the cost of in-flight non-finalized work).
- **Signing paperwork** blocks M10. Mitigation: start in M1; Linux first.
- **Updater key compromise or loss.** Mitigation: `release` environment with reviewer, offline escrow with two custodians, rotation/compromise runbook, updates opt-in, keyless cosign on every asset for out-of-band verification.
- **Grafana iframe blocked on macOS** or unreachable from Docker Desktop. Mitigation: tested in M7; open-in-browser fallback; status strip is primary.
- **Tauri v3** may end v2 support. Mitigation: pin `2.x`, keep the Tauri surface thin (one bridge crate, commands + Channel only), avoid `v1Compatible` artifacts.
- **Leptos yearly breaking minor / trunk gaps.** Mitigation: CSR-only, grouped dependabot, logic in native crates, hand-written externs.
- **Scheduled workflows disable after 60 idle days.** Mitigation: Zebra release checklist is the primary trigger; monthly dependency merges keep the repo active.
